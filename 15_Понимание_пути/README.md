# Этап15: понимание пути

Запуск: `Запустить_понимание_пути.bat`. Также доступен пункт финального модуля «Понимание пути, балласт и сравнение сопровождения».

1. Откройте фотографию или первый кадр видео; выберите завершённые локальные веса. Нажмите CPU-сегментацию. Без этого сохраняется статус неизвестной геометрии.
2. Модель `yolo26s_straight_track_seg_best.pt` имеет классыrail_left/rail_right/sleeper/fastener/ballast. Коридор выводится между видимыми рельсами. МодельRailSem19 rail/trackbed можно подключить после её отдельного обучения; базовые COCO-веса не считаются моделью пути.
3. На стрелке включите соответствующий флаг и подтвердите кандидат. Несколько путей также блокируют автоматический выбор. Выбор переносится только при непрерывной совместимой геометрии; после потери выбора требуется повтор. Самостоятельно распознавать все стрелки модель пока не умеет.
4. Пробная рамка позволяет проверить положение человека/камня/балласта. Это рамка пользователя, а не новая детекция. Вне коридора камень сохраняется как контекст; внутри на балласте — кандидат для проверки, не доказанная опасность. Семантическийballast не создаёт событие.
5. Метры появятся только в рамках пользовательской калибровки плоскости с независимыми проверочными точками, подходящими источником/разрешением и областью. Без неё остаютсяпиксели/unknown. Шаблон экспортируется пустым; он не является калибровкой.
6. Для живого канала примените настройки, запустите источник самостоятельно, возьмите свежий снимок результата и подтвердите ветку. Сегментация выполняется CPU на том же исходном кадре. Источник/GPU/обучение модуль сам не запускает. CPU-сегментация добавляет задержку: при превышении допустимого возраста кадр/геометрия отклоняются.
7. Сравнение принимает замороженные одинаковые детекции и вручную проверенные GT с постояннымиID. Встроенные синтетические сценарии проверяют программное поведение; они не доказывают улучшение на реальных видео.

Подробности: `Методика_и_ограничения.md`; программные/инференс-проверки: `verification.json`; примеры сравнения: `tracking_occlusion` и `tracking_acceleration`; трудные отрицательные регионы: `hard_negatives`. Для рабочего решения пока остаются независимые видео с ручными GT.

## Результат проверки текущей версии

Актуальный протокол — `verification.json`, полный журнал — `tests_cpu.log`.
Ссылки на последние сравнения с подсчётом реальных карточек EventAssociator —
`latest_tracking_reports.json` (папки с суффиксом `_cards`). Старые отчёты без этого
суффикса оставлены как предыдущие результаты.

Выполнен реальный CPU-инференс существующих весов
`yolo26s_straight_track_seg_best.pt` на первом центральном кадре OSDaR:
1920×1168, imgsz=640, conf=0.35. Рельсы не найдены, коридор UNKNOWN.
Результат: `real_CPU_segmentation/geometry.json`; вид — `preview_real_unknown.png`.
Это ограничение текущих весов: программный модуль готов к подключению модели,
но качество сегментации пути на реальных сценах пока не подтверждено.
Порог по этому кадру не подбирали. Время одного вызова не является оценкой FPS системы.
Обучение и GPU не запускались, файл весов проверен по SHA256 и не изменён.

На синтетическом перекрытии повторные карточки: IoU — 1, ByteTrack — 0.
При ускорении и снижении confidence: IoU — 1, ByteTrack — 2;
у ByteTrack также 4 пропущенных видимых наблюдения из 30. Поэтому IoU оставлен
по умолчанию; переход на ByteTrack требует проверки на вашей независимой записи.
Это карточки кандидатов при отключённом фильтре пути, не подтверждённые оператором тревоги.

`hard_negatives/contact_sheet.png` показывает 4 небольших региона ранее использованных
кадров. Они не выданы за независимые GT: три — кандидаты обычного фона для
подтверждения человеком, в `left_trackbed` виден белый предмет, поэтому регион
оставлен неоднозначным. Статусы — `hard_negatives/regions_review.json`.
`hard_negatives/functional_context_checks.json` проверяет пять программных случаев на явно
синтетических масках/рамках. Нулевую частоту ложных тревог на настоящем видео
эти проверки не доказывают.

Демонстрация: откройте два пути → попробуйте рамку без выбора → подтвердите ветку →
повторите проверку камня внутри и снаружи. Скриншоты до/после —
`preview_switch_unconfirmed.png`, `preview_switch_confirmed.png`.
Следующий измерительный шаг: независимые видео с масками рельсов/ego-track,
постоянными ID объектов, трудными отрицательными и положительными камнями,
проверкой пригодности кадров; затем сравнение до/после обучения.

## Получить одинаковые детекции для реального сравнения

При включённом модуле пути в `telemetry.jsonl` сессии записываются исходные рамки,
классы, хеш весов детектора, источник, номер и хеш кадра, время и пригодность изображения.
После записи экспортируйте шаблон из папки приложения:

```text
python export_path_tracking_template.py ПУТЬ_К_telemetry.jsonl comparison_GT.json 0 1
```

Последние числа — канал и поколение источника из журнала. Разные источники,
разрешения и веса не смешиваются. Скрипт сохраняет детекции без изменений,
оставляет `reviewed=false` и пустые `ground_truth`: это ещё НЕ отрицательная разметка.
По исходной записи внесите для каждого видимого объекта устойчивый `id`, `class_name`
и `box: [x1,y1,x2,y2]`, затем подтвердите проверенные кадры `reviewed=true`.
Непригодные интервалы разметьте отдельно в оценке событий этапа12; их нельзя
считать проверенными пустыми сценами. У файлов используется время видеозаписи,
у камеры — время захвата. Загрузите готовый JSON на вкладке сравнения.
Оба трекера получат одинаковые рамки. Полноценная запись оригинального видео
не заменяется журналом рамок: исходные изображения нужны для независимой разметки.
