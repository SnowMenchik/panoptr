# Карта рейсов Panoptr

Дополнительный модуль общей памяти наблюдений между рейсами. Он принимает **события**, а не все видеопотоки: непрерывный анализ камер остаётся в основном приложении. Событие содержит время, поезд и рейс, тип находки, качество наблюдения и при наличии проверенное место объекта. Реализована схема по километражу линии и пути, без скачивания карт и без зависимости от интернета.

## Запуск и демонстрация

Из финальной сборки: кнопка **«Карта рейсов»**. Отдельно: `../Запустить_карту_рейсов.bat`. Камеры и модели автоматически не запускаются; GPU модулю не нужен.

1. Откройте «Демо двух рейсов». Демо работает в отдельной временной базе и не смешивается с рабочими находками.
2. Дефект на 125-м км повторно наблюдался двумя рейсами; человек на 127-м км подтверждён; камень на 130-м км устарел для подтверждения; наблюдение на 131-м км плохого качества. БПЛА сохранён без координат.
3. Нажмите точку на схеме или строку таблицы: справа история. Фильтры разделяют линии, пути и статусы.
4. Вкладка «Следующий рейс»: положение 124 км, направление по возрастанию, глубина 10 км. Видны только свежие подтверждённые предупреждения впереди. Предупреждение о человеке истечёт через две минуты после наблюдения.
5. «Отклонить» и «Закрыть по проверке» требуют имени оператора и основания; все решения сохраняются в аудите. Снимки из подключённого локального журнала показываются в карточке.

## Приём существующего журнала

«Подключить журнал» принимает папку с `session.json` и `events/<event_id>/event.json`. При открытии из основного окна диалог выбора начинается с текущей сессии. Укажите ID поезда и уникальный ID рейса. Новые события читаются каждые три секунды, до 200 за цикл; повторы не создаются. Повторным нажатием можно выбрать другой журнал.

Исходное `created_utc` — время регистрации события на компьютере, а не гарантированное время экспозиции камеры. Качество берётся из исходного доказательства. Изменение `hits` в основном приложении не создаёт новый объект карты. Решения оператора из локального детектора не переносятся автоматически в общую карту: здесь проверяется также место и актуальность.

При отсутствии геопривязки событие попадает во вкладку **«Без места»**. Можно указать проверенный километраж именно объекта, путь и погрешность с именем оператора. Все такие действия записываются в аудит. Внешний адаптер поезда может передать `object_location` в метаданных `provenance` исходного доказательства, либо отправить отдельный пакет по API. Камера, пиксели рамки и GNSS поезда сами по себе не дают координату удалённого объекта. Нужны синхронизация, калибровка и проверка пути; при их отсутствии координаты не выдумываются.

## API и передача с поезда

Кнопка «Приём от поезда» открывает HTTP-приёмник только на `127.0.0.1` со случайным портом и Bearer-токеном. Он выключен по умолчанию. Повторное нажатие или закрытие окна его останавливает. Токен показывается только в диалоге подключения и меняется при новом запуске приёмника.

- `POST /v1/observations` — атомарная доставка пакета: максимум 1000 наблюдений, до 2 МБ через API.
- `GET /health` — состояние приёмника, также с токеном.
- `GET /v1/warnings?route_id=R&track_id=I&chainage_m=124000&direction=1&lookahead_m=10000&run_id=NEXT` — предупреждения для следующего рейса. `direction=-1` для обратного направления. Ответ никогда не удостоверяет свободный путь.
- Все запросы: заголовок `Authorization: Bearer <token>`.

Для удалённого поезда нужен HTTPS-шлюз/VPN до локального приёмника; внешнее сетевое развёртывание и удостоверение личности оператора не настраиваются автоматически. Не публикуйте этот HTTP-порт напрямую в интернет.

Формат пакета (время в примере замените на текущее):

```json
{
  "schema": "panoptr.route.v1",
  "train_id": "TRAIN-01",
  "run_id": "RUN-2026-10-19-01",
  "observations": [{
    "observation_id": "unique-stable-id",
    "kind": "track_defect",
    "observed_at": "2026-10-19T09:00:00+00:00",
    "quality_ok": true,
    "confidence": 0.87,
    "location": {
      "route_id": "MSK-SPB",
      "track_id": "I",
      "chainage_m": 125000,
      "uncertainty_m": 3,
      "position_kind": "object",
      "verified": true
    }
  }]
}
```

Типы: `person`, `drone`, `rock`, `obstacle`, `track_defect`, `contact_defect`. При неизвестном месте передайте `location: null`. Координаты WGS84 `latitude` и `longitude` можно передавать парой в `location`, но отрисовка использует линейный километраж, не GPS-подложку. Неизвестное место, координата поезда, непроверенное место или погрешность более 25 м исключаются из предупреждений.

Идентичность доставки: `(train_id, run_id, observation_id)`. Повтор идентичного пакета безопасен; тот же ID с другим содержимым отклоняется целиком. Решения оператора нельзя подменить полями входного пакета. Файл `.json` содержит один пакет; `.jsonl` — по пакету в строке. При ошибке в очередном пакете уже принятые предыдущие пакеты JSONL остаются принятыми; повтор импорта безопасен. База SQLite сохраняет наблюдения, находки и аудит между запусками; экспорт архива не является входным пакетом.

`route_train_sender.py` — отправитель со стороны поезда. Сначала сохраняет пакеты в `pending` на диск, после подтверждения сервера переносит в `sent`. При потере связи исходные ID и данные сохраняются, повтор доставки не размножает события. Пример из папки реализации с доступным Python:

```text
python route_train_sender.py --session "путь_к_сессии" --train-id TRAIN-01 --run-id RUN-001 --outbox "путь_к_очереди"
```

Без `--url` это только подготовка очереди, без передачи. Для отправки добавьте `--url http://127.0.0.1:ПОРТ/v1/observations` и установите переменную окружения `PANOPTR_ROUTE_TOKEN`. `--watch` включает повторный сбор и отправку каждые 5 секунд до остановки пользователем. Для удалённого адреса отправитель требует HTTPS и проверяет сертификат стандартной библиотекой Python.

## Новое, повторное, устаревшее

Сопоставление требует одинаковых линии, пути и типа. Радиус — сумма погрешностей, ограниченная диапазоном 5-30 м. Это гипотеза о совпадении места, не доказанная идентичность физического объекта. Близкие разные дефекты пока могут объединиться: для производственной установки понадобятся идентификатор элемента пути, геометрия, изображения и отдельная оценка ошибок сопоставления. Для человека/БПЛА отображается **«Повторная зона»**, а не утверждение, что это тот же человек или аппарат. Временные опасности разделяются также по времени.

Текущие консервативные демонстрационные сроки от времени наблюдения: человек/БПЛА 120 с, камень/препятствие 600 с, дефекты пути/контакта 86400 с. Это настройки прототипа, не утверждённые эксплуатационные нормы. После истечения предупреждение исчезает из выдачи, но находка остаётся в истории как устаревшая. Истечение не означает устранение опасности.

Только оператор может подтвердить свежее качественное наблюдение с проверенным местом. Следующая детекция не продлевает подтверждение автоматически; повторное подтверждение привязывается к новому пригодному наблюдению. Плохой кадр, отсутствие связи и отсутствие детекции не закрывают находку. Закрытие требует отдельного решения с основанием; это не автоматическое «свободно». Выдача учитывает выбранные линию/путь, направление, положение и глубину просмотра; сведения из текущего ID рейса исключаются из выдачи этому же рейсу.

## Границы реализации

Реализованы локальный приём событий, дисковая очередь отправителя, накопление между рейсами, схема участка, просмотр доказательств локальной сессии, ручная геопривязка, подтверждение/закрытие, актуальность и API выдачи предупреждений. Передача видеопотоков, натурная GNSS/одометрия, калибровка места объекта, диспетчерский сервер в инфраструктуре РЖД, автоматическая синхронизация часов и управление движением сюда не входят. Круглосуточная производственная эксплуатация потребует проверки этих компонентов и регламента операторов.
