# Отказоустойчивость хранилища PANOPTR

Документ описывает маршрутизацию записей и чтений между независимыми узлами
хранения, ручное управление узлами и реальные гарантии сохранности данных.

## 1. Что считается узлом хранения

Узел — это независимый корень файловой системы:

- внутренний или внешний диск;
- смонтированный сетевой ресурс (SMB/NFS);
- отдельная локальная папка.

Проект не содержит распределённой СУБД или кластера, поэтому узлом не может быть
«сервер базы данных»: маршрутизация работает на уровне файловых операций
`EventStore` / `ArchiveStore` (`final_store.py`). Сами узлы описаны в
`config.json` и обслуживаются модулем `storage_failover.py`.

Если узлы не заданы, создаётся один узел — папка сессии. Поведение прежней
версии при этом сохраняется: все файлы лежат в одной папке, API `EventStore`
не меняется.

## 2. Состояния узла

| Состояние | Значение |
|---|---|
| `ACTIVE` | Узел доступен, участвует в чтении и записи. |
| `UNAVAILABLE` | Операция или проверка завершилась ошибкой/таймаутом. Узел исключён из маршрутизации до успешной проверки. |
| `DISABLED` | Узел отключён оператором. Автоматические проверки не возвращают его в работу. |
| `RECOVERING` | Узел проверяется и синхронизируется; в маршрутизации пока не участвует. |

Переходы:

- `ACTIVE → UNAVAILABLE` — ошибка ввода-вывода, таймаут или превышение
  `failure_threshold` подряд идущих ошибок;
- `UNAVAILABLE → RECOVERING → ACTIVE` — успешная проверка и, если включено,
  синхронизация с исправного узла;
- `ACTIVE/UNAVAILABLE → DISABLED` — команда оператора;
- `DISABLED → RECOVERING → ACTIVE` — команда оператора и успешная проверка.

## 3. Настройка

Секция `storage` в `config.json`:

```json
{
  "storage": {
    "nodes": [
      {"id": "disk-a", "root": "D:/panoptr_store", "priority": 0},
      {"id": "nas-b", "root": "//nas/panoptr", "priority": 1}
    ],
    "session_subdir": true,
    "failover": {
      "connect_timeout_s": 2.0,
      "operation_timeout_s": 10.0,
      "max_attempts": 3,
      "retry_backoff_s": 0.05,
      "failure_threshold": 1,
      "recovery_interval_s": 5.0,
      "monitor_interval_s": 2.0,
      "replicate_writes": true,
      "sync_on_recovery": true
    }
  }
}
```

Параметры:

- `nodes` — список узлов. `root` может быть абсолютным или относительным
  (относительный путь считается от папки `panoptr`). Пустой список означает
  один узел — папку сессии.
- `session_subdir` — создавать внутри каждого `root` подпапку с именем сессии.
  Это удобно, если один диск используется несколькими запусками. Можно
  переопределить для отдельного узла полем `session_subdir`.
- `connect_timeout_s` — предел проверки доступности узла.
- `operation_timeout_s` — предел одной файловой операции на узле.
- `max_attempts` — максимум узлов, которые пробует одна операция `execute`;
  не даёт бесконечно переключаться между узлами.
- `retry_backoff_s` — резерв для паузы между повторными попытками.
- `failure_threshold` — сколько ошибок подряд переводят узел в `UNAVAILABLE`.
- `recovery_interval_s` — минимальный интервал между проверками недоступного
  узла.
- `monitor_interval_s` — период фоновой проверки; `0` отключает монитор.
- `replicate_writes` — синхронно дублировать запись на все доступные узлы.
- `sync_on_recovery` — перед возвратом узла в `ACTIVE` догонять его с
  исправного узла.

Старый `config.json` без секции `storage` продолжает работать.

## 4. Алгоритм

1. Перед операцией выбираются узлы в состоянии `ACTIVE` (отключённые вручную
   исключены всегда).
2. Запись (`write_text`, `write_bytes`, `append_text`, `commit_tree`)
   выполняется на все выбранные узлы. Успех — если запись принял хотя бы один
   узел. Число сохранённых копий возвращается вызывающему коду.
3. Если часть узлов не ответила, они переводятся в `UNAVAILABLE`, а в журнал
   добавляется событие `degraded_write` / `degraded_append` /
   `degraded_commit`. Вызывающий код не получает ложное «сохранено везде».
4. Если не ответил ни один узел, выбрасывается `StorageUnavailableError`.
   `EventStore.submit` в этом случае возвращает `False`, а `flush()` фиксирует
   ошибку в `EventStore.error`; событие не появляется в `events()`.
5. Чтение (`read_text`, `read_bytes`, `find_path`, `list_files`) опрашивает
   доступные узлы и выбирает самый новый файл. Если копии различаются, в журнал
   пишется `read_conflict`.
6. Недоступный узел проверяется монитором или явным `probe_due(force=True)`.
   Проверка пишет служебный маркер `.panoptr_node.json` и читает его обратно.
7. Перед возвратом узла в `ACTIVE` выполняется синхронизация: файлы с более
   новой датой копируются на возвращающийся узел; JSONL-журналы объединяются
   построчно, поэтому строки, существующие только на одной стороне, не
   теряются. Данные с возвращающегося узла не удаляются.
8. Ручное отключение выставляет `manual_disabled`; автоматические проверки такой
   узел не включают. Ручное включение снимает флаг, переводит узел в
   `RECOVERING` и возвращает `ACTIVE` только после успешной проверки и
   синхронизации.

## 5. Ручное управление

В интерфейсе «События и финал» есть вкладка **«Узлы хранения»**. На ней
показаны состояние, папка, последняя ошибка, счётчики операций и время
следующей проверки. Кнопки:

- **Обновить состояние** — прочитать текущие состояния;
- **Отключить выбранный** — перевести узел в `DISABLED` и исключить его из
  новых записей и чтений;
- **Включить и проверить** — снять ручную блокировку, проверить узел и
  синхронизировать его; при ошибке узел останется недоступным;
- **Синхронизировать** — вручную догнать включённый узел с исправного.

Те же действия доступны из кода:

```python
store.node_statuses()                 # список состояний
store.storage_status()                # состояния + настройки + история
store.disable_node("disk-a", "плановое обслуживание")
store.enable_node("disk-a")           # вернёт ACTIVE только после проверки
store.sync_node("disk-a")
store.active_root                     # текущий узел для новых файлов
```

## 6. Гарантии и ограничения

Что гарантируется:

- при доступном хотя бы одном узле запись не теряется и не блокирует захват
  кадров;
- при нескольких доступных узлах успешная запись синхронно создаётся на всех
  доступных узлах;
- после восстановления узел получает пропущенные данные перед возвратом в
  работу;
- ручное отключение не отменяется автоматикой;
- состояние и причины ошибок видны в интерфейсе и экспортируемом отчёте.

Чего не гарантируется:

- это **не резервное копирование и не консенсус-репликация**: нет кворума,
  журнала транзакций и защиты от «разделения мозга» при сетевом разделении;
- при падении всех узлов новые данные не сохраняются; приложение сообщает об
  ошибке, но не восстанавливает потерянное;
- запись на несколько узлов не является атомарной: если узел упадёт между
  копиями, часть узлов может остаться без файла. Такая запись помечается как
  частичная (`degraded_*`), а при возврате узла синхронизация догонит его;
- при конфликте разных версий одного файла выбирается более новый по времени
  изменения; автоматического слияния JSON-файлов нет (кроме JSONL);
- таймаут не убивает зависший системный вызов: поток-жертва остаётся
  демоном, но узел исключается из маршрутизации и синхронизируется перед
  повторным использованием;
- узлы — только файловые пути, без встроенного сетевого протокола и
  шифрования; права доступа определяются операционной системой.
