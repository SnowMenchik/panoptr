Для новой версии используйте **`run_final_offline.bat`**: CPU по умолчанию, без pip и скачивания при старте. Добавлены привязка результата к исходному кадру, generation/sequence, согласованный буфер, контроль качества/покрытия и **«События и финал»** с доказательствами, операторским решением, CPU-репетицией и проверкой данных. Хранилище может работать с несколькими независимыми узлами (дисками или
смонтированными сетевыми папками): при отказе одного узла запись и чтение
продолжаются на доступных, а вернувшийся узел синхронизируется. Настройка,
ручное отключение/включение и честные гарантии описаны в
[STORAGE_FAILOVER_RU.md](STORAGE_FAILOVER_RU.md).

Добавлена **«Лаборатория данных»**: проверка изображений и масок, подготовка
наборов, обучение/дообучение, сравнение моделей и экспорт предсказаний.
Она запускается отдельным процессом из панели или `run_dataset_lab.bat`.
Инструкция: `dataset_lab/README_RU.md`. Проверка данных не использует GPU;
обучение запускается явно пользователем.

В панели инструментов доступен **«Симулятор ВСМ»**. Он запускается
в независимом процессе, обрабатывает записанное видео с имитацией скорости,
погоды, отказов, перегрузки и формирует CSV/JSON-метрики. Описание находится
в `vsm_simulator/README_RU.md`.

В списке моделей доступна обученная модель **Человек — своя модель**. 
Для максимальной чувствительности к небольшим силуэтам можно выбрать размер 960; 
для более высокой скорости — 640.

Также в приложение встроены лучшие модели диагностики пантографа V2:

- **«Пантограф — локатор V2»** — поиск пантографа, рекомендуемый размер 1024;
- **«Пантограф — точка контакта V2»** — вспомогательная геометрия контакта, размер 1280;
- **«Пантограф — искрение V2»** — обнаружение дуги/искрения, размер 960.

Для диагностики пути добавлены две специализированные модели:

- **«Крепления — диагностика RFDD V1»** — классы normal, missing, displaced,
  inverted, deformed и fractured; рекомендуемый размер 1280;
- **«Путь — сегментация компонентов V1»** — маски rail_left, rail_right,
  sleeper, fastener и ballast; рекомендуемый размер 1024.

При выборе этих пунктов рекомендуемый размер устанавливается автоматически.

Готовый MVP для одновременного показа двух USB-камер. У каждой камеры собственная
YOLO26-модель и собственные параметры, а общий планировщик выполняет инференс
последовательно и всегда обрабатывает только самый свежий кадр.

В каждой панели доступны три встроенных варианта модели:

- `yolo26n.pt` — детекция объектов;
- `yolo26s-seg.pt` — общая детекция с полупрозрачными масками сегментации, локальная копия имеющихся весов;
- `yolo26n-pose.pt` — обнаружение людей, ключевых точек и скелета.

Также можно выбрать собственный файл модели. В двух панелях разрешено одновременно
использовать разные типы задач.

Захват каждой камеры работает в отдельном изолированном процессе. YOLO-модели остаются
в одном GPU-планировщике, чтобы дважды не занимать видеопамять.

## Быстрый запуск на Windows

1. Установите Python 3.11 или 3.12 x64 с сайта python.org и включите пункт
   `Add Python to PATH`.
2. Подключите две веб-камеры.
3. Дважды щёлкните `run.bat`.
4. В окне нажмите **Запустить обе**.

Приложение показывает названия устройств из Windows, а не только числовые индексы.
Если камера была подключена после запуска программы, нажмите **Обновить камеры**.
Источники NVIDIA Broadcast, OBS и другие программные камеры отмечаются как
`виртуальная`: они могут намеренно повторять изображение физической веб-камеры.

При первом запуске устанавливаются зависимости. Файл `yolo26n.pt` загружает
Ultralytics автоматически при первом инференсе, поэтому в этот момент нужен интернет.
После загрузки приложение может работать локально.

Ручной запуск:

```powershell
py -3.11 -m venv .venv
.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
python main.py
```

## Настройки по умолчанию

- Камеры: индексы 0 и 1.
- Захват: 640×480, запрос 15 FPS — надёжный режим для двух USB-камер.
- Модель: `yolo26n.pt` отдельно для каждой камеры.
- Инференс: 512 px и не более 8 кадров/с на камеру.
- Устройство: `Auto` — NVIDIA CUDA при наличии, иначе CPU.
- Очередь: один последний кадр на камеру, без накопления задержки.
- Объект драйвера никогда не освобождается из интерфейсного
  потока — это предотвращает аварийное завершение с некоторыми Logitech-камерами.
- Если драйвер полностью блокируется, watchdog завершает только процесс этой камеры и
  запускает его снова. После повторного зависания используется 320×240 при 15 FPS.
- Последние рамки YOLO рисуются поверх текущего кадра, поэтому живое видео не зависит
  от частоты инференса.

Можно выбрать разные `.pt`, `.onnx` или `.engine` модели непосредственно в каждой
панели. Изменение модели или устройства применяется при следующем инференсе; камера
при этом продолжает показывать изображение.

## Если компьютер слабый

- установите размер 416 или 320;
- уменьшите «Анализ FPS» до 3–5;
- оставьте модель размера `n`;
- уменьшите разрешение захвата в `config.json` до 640×480.

## Если есть NVIDIA GPU

Для первого теста достаточно режима `Auto`. Для постоянной установки рекомендуется
экспортировать каждую модель в TensorRT FP16 на том компьютере, где она будет
использоваться:

```powershell
yolo export model=your_model.pt format=engine half=True imgsz=512 device=0
```

Затем выберите полученный `.engine` в панели камеры. TensorRT engine зависит от
конкретного семейства GPU и версии TensorRT, поэтому переносить готовый engine между
произвольными компьютерами не следует.

Если интерфейс сообщает, что NVIDIA CUDA недоступна, закройте приложение и запустите
`install_nvidia_cuda.bat`. Скрипт сначала проверит наличие драйвера NVIDIA, затем
установит официальную CUDA-сборку PyTorch. Для AMD и Intel этот установщик применять
не нужно: текущий backend моделей `.pt` использует их через CPU.

## Диагностика камер

Выберите нужное устройство по названию в каждой панели. Одну физическую камеру нельзя
одновременно открывать в двух панелях. Если камера найдена, но не отдаёт кадры,
приложение автоматически попробует DirectShow, Media Foundation и системный backend.

Некоторые USB-контроллеры не выдерживают два несжатых потока 1280×720. В таком случае
подключите камеры к разным USB-контроллерам или установите 640×480 в `config.json`.

## Виртуальный 3D-стенд для финала

Запустите `run_virtual_stand.bat` или откройте соответствующий пункт финального
модуля. Стенд использует CPU: компоновка двух камер, разбор кожуха, сменные вставки,
каретка, свет, заслонка, журнал и шесть повторяемых синтетических сценариев.
Это проверка демонстрационного цикла с метками из геометрии; YOLO и обучение не запускаются.

CAD, расчёты, смета с источниками и программа будущих аппаратных испытаний лежат
в `../../14_Виртуальный_3D_стенд`. Индустриальные камеры требуют отдельного SDK-адаптера;
реальный захват и работа на ВСМ этой виртуальной версией не подтверждаются.

## Понимание пути и сопровождение

Запуск: `run_path_understanding.bat`; тот же инструмент доступен из финального модуля.
Сегментация работает на CPU и включается в канале явным применением настроек.
Видимые рельсы, кандидаты коридора, подтверждение пути на стрелках, контроль
свежести/качества, контекст камней и сравнение IoU с ByteTrack сохраняют происхождение
результата. Неизвестная геометрия не даёт метров и не означает свободный путь.

Материалы и результаты: `../../15_Понимание_пути/README.md`.
Текущие старые веса не выделили рельсы на проверенном кадре OSDaR:
для рабочей точности нужны подходящие обученные веса и независимая разметка.
Сравнение трекеров на синтетике проверяет программное поведение.
Проверка выпуска: `python verify_path_release.py` (CPU, без обучения и загрузок).
